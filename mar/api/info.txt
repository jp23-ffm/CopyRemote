● Oui, c'est fait, sans trop d'effort. Une seule modification, dans api/views_v2.py (QueryBuilderView).

  Ce qui change :
  - Le JSON accepte une nouvelle clé optionnelle model_to_use, en minuscules comme les autres clés
    (query_builder_exclude, categories).
  - La valeur peut être le nom du modèle seul, cherché dans l'app du JSON : "model_to_use": "Schedpatch".
  - Elle peut aussi préciser l'app : "model_to_use": "autreapp.Schedpatch".
  - Quand la clé est là, seuls les champs du JSON qui existent vraiment sur ce modèle sont proposés.
  - Les clés de SrvPropView.ALIAS_MAP restent autorisées, sinon priority_asset & co disparaîtraient de la liste.
  - Sans la clé, ou avec un modèle introuvable, la liste reste comme avant. Un nom de modèle introuvable écrit en plus
    un warning dans le logger chimera.api.

  À savoir : le filtre s'applique au niveau de l'index, donc à toutes les listes du builder (champs, filtres, unify,
  enrich) et pas seulement à l'Enrich. Je pense que c'est ce qu'on veut : un champ absent du modèle ne fonctionne nulle
  part.

  Vérifié :
  - manage.py check ne remonte aucune erreur.
  - J'ai testé la fonction de résolution dans manage.py shell : modèle seul, app.Model et nom invalide se comportent
    comme prévu.
  - Je n'ai pas chargé la page du builder dans le navigateur. Comme aucun JSON ici n'a la clé, l'affichage actuel ne
    bouge pas.

  En passant : sur inventory.Server, il n'y a pas de champ HOSTNAME (il y a SERVER_ID, SERVER_IP…). Si tu mets
  model_to_use sur l'inventory, HOSTNAME disparaîtra de la liste, s'il est dans le JSON.

  Pour ton autre app, il suffit d'ajouter "model_to_use": "Schedpatch" à la racine de son field_labels.json. Il faut
  aussi que l'app soit lue par le builder : pour l'instant la boucle ne lit que inventory, businesscontinuity et
  discrepancies.

● Un tag par entrée demanderait quand même du code. La vue construit la liste elle-même, donc il faudrait qu'elle lise
  ce nouveau flag : une ligne dans le filtre de QueryBuilderView, du genre and props.get('query_builder', True). Pas
  énorme, mais pas zéro.

  Par contre, ce que tu veux existe déjà sans toucher au code. Le bloc query_builder_exclude du JSON accepte une liste
  de champs :

  "query_builder_exclude": {
      "categories": [],
      "fields": ["CHAMP_A", "CHAMP_B"]
  }

  Les deux solutions manuelles ont le même défaut : il faut tenir la liste à jour à la main. Avec beaucoup de champs qui
  ne sont pas au bon modèle, c'est fastidieux et ça dérive avec le temps. model_to_use filtre tout seul à partir du
  vrai modèle et reste juste si le modèle change.

  Ma recommandation : garder model_to_use pour le gros du tri, et query_builder_exclude.fields pour les quelques
  exceptions.
