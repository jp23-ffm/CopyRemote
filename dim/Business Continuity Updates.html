Business Continuity Updates

Business Continuity, November 2026

Less risk of error in every bulk change

Before applying a change, teams see exactly what will move, server by server. Afterwards, every modification is tracked and a mistake can be reversed from an export.

See before actingA detailed review step for rules, imports and bulk edits.
Recover from mistakesThe server state export can be loaded straight back through the import.
Find everything laterA more reliable history and an import journal.

Apply BC Rules

The workflow now starts from the server list filters and also handles the site that is not involved in the Live Play.

BeforeNow
A datacenter was picked from a row of buttons.Scope taken from the list filters: one datacenter is required, then as many criteria as needed.
The sibling site had to be reset separately with a bulk edit.Automatic, optional reset of the sibling datacenter, directly in the workflow.
A server present on both sites was not flagged.It receives the rule without being reset, and a warning flags it. Skipped servers that keep an action are listed too.
The confirmation showed totals.Clickable lists of modified and unchanged servers, for each rule and for the sibling site.
The final page replaced the progress view.Progress and summary on the same page, including after a failure.
A rule could be applied with an empty text.Empty texts are refused. To set nothing, users enter EMPTY.

CSV imports

Three formats now share the same workflow: server import, full export and application import.

DB35501D  action_during_lp: BAD BULK → STOP BEFORE LP
SRV15107P priority_asset: WRONG → NO

Example of the review step before an import, using test data.

BeforeNow
Restoring a state meant rebuilding a file in the right format.The export file loads as is. The import reduces it to one line per server and restores the values, empty fields included.
A simple “import N records?” prompt.Review page: servers modified, up to date or not found, count per field, and old → new value with search.
A wrong value went into the database; a malformed file was rejected outright.Imperfect files handled with care: spaces and case are fixed, invalid lines are ignored and listed with the reason.
Application import gave no detail.The same review, with the reason for each change, such as which applications move a server to YES.
The result disappeared with the page.Import journal (who, when, which file, outcome) and full details downloadable as CSV.
After a failure, there was no way to know how far the import had gone.The summary shows what was saved and what was not, and a rerun only processes the rest.

Bulk edit

This is the operation most exposed to handling errors. It now has the same protection as the imports.

BeforeNow
An “are you sure?” prompt.Change review before applying: real number of servers, old → new value, and search in the list.
Nothing warned about an overly wide selection.Warning when no filter is active, before applying to every server in the view.
Servers already holding the right value were rewritten.Only real changes are applied, and the button states the exact number of servers.
Entered values stayed from one opening to the next.The form starts empty, so an old text cannot be applied to another selection. The Apply button locks as soon as it is clicked.

Traceability and API

BeforeNow
Some changes left no trace.All modifications are recorded, including bulk edit resets to EMPTY and DR Reset history wipes.
The author of an edit was sent by the browser.The author now comes from the logged-in user's session.
The history filled up with entries that changed nothing.A more readable history: imports, bulk edits and rules only write what changes.
The last modification date was not available in the API.New last_modified field in the API and the Query Builder.
“Original Action During LP” column.Renamed “Annotation” in the screens, exports and API.

Bugs fixed

What users sawNow
Typing “SRV1, SRV2” in a filter created an empty entry and the filter stopped filtering.Fixed on all filtered pages: Business Continuity, Inventory, Applications, Discrepancies, Hardware and Storage.
A failed application import was displayed in green, like a success.An import with no effect is clearly announced before anything starts.
A file saved from Excel as “CSV UTF-8” was refused for an incorrect header.These files are accepted.
A file with the wrong encoding caused an incomprehensible technical error.The message states that the file must be UTF-8.
A text containing a semicolon or a line break caused the import to be rejected.These texts now go through, when quoted in the CSV.
The bulk edit showed the number of lines as a number of servers (10001 instead of 5000).The number shown is the servers actually concerned.
A bulk edit reset to EMPTY did not appear on the Changes page.It now appears, with its author and date.
Requesting an unknown field from the API returned a server error.The API answers with a clear message naming the field.
These changes are covered by 73 automated tests, which can be rerun after every new modification.
