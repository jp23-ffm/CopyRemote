Patching CSV Import

Patching CSV import

Every 15 minutes, a CSV file of about 70,000 servers is loaded into Postgres. Only rows that actually changed are written, and nothing is ever deleted: a server missing from the file stays in the database as it is.

Import steps

Trigger

1

Scheduled run

A cron job (or systemd timer) runs the command every 15 minutes, outside Django web requests.

manage.py import_patching <file.csv>
2

Overlap lock

A Postgres lock ensures only one import runs at a time, even if the previous one takes longer than 15 minutes.

pg_try_advisory_lock(...)
Lock already heldAn import is running: exit without doing anything.
3

Same file as last time?

The file hash is compared with the hash of the last successful import. Outside patching campaigns, this is the most frequent case.

sha256(file) == last hash
IdenticalNothing to do, exit. Almost zero cost.

Preparation in Python

4

Read and clean the CSV

  • ; delimiter, extra empty column from the trailing ; ignored
  • Column names: __ → _ (Django forbids double underscores in field names)
  • null → EMPTY on the relevant fields
  • All fields stay strings

One single Postgres transaction: all or nothing

5

Create the staging table

Temporary table with the same columns as the real table. Only visible to this import, no Django model and no migration.

CREATE TEMP TABLE ... ON COMMIT DROP
Error at any stepROLLBACK: the database stays exactly as before, the staging table disappears.
6

Bulk load into staging

The 70,000 cleaned rows are sent in one block. About one second, with no Postgres write-ahead log.

COPY patching_staging FROM STDIN
7

Upsert into the real table

One SQL query compares every staging row with the database and decides what to do (see the per-row flowchart below).

INSERT ... ON CONFLICT (servername) DO UPDATE ... WHERE ... IS DISTINCT FROM ...

End

8

COMMIT

Users see the new state all at once, never a partial one. The staging table is dropped automatically.

9

Store the hash

The file hash is saved for step 3 of the next import, then the lock is released.

Import doneFrom 0 to a few thousand rows written, depending on the period.

Flowcharts

The same logic as above, as decision diagrams.

Whole import

flowchart TD
    A(["Cron, every 15 min"]) --> B{"Lock acquired?"}
    B -- No --> X1(["Exit: import already running"])
    B -- Yes --> C["Compute file SHA-256"]
    C --> D{"Same hash as last import?"}
    D -- Yes --> X2(["Release lock, exit"])
    D -- No --> E["Read and clean CSV"]
    E --> F["BEGIN transaction"]
    F --> G["CREATE TEMP TABLE staging"]
    G --> H["COPY rows into staging"]
    H --> I["Upsert into patching_server"]
    I --> J{"Error?"}
    J -- Yes --> K["ROLLBACK, database unchanged"]
    K --> X3(["Release lock, log error"])
    J -- No --> L["COMMIT, staging dropped"]
    L --> M["Store file hash"]
    M --> X4(["Release lock, done"])

Upsert, for each row

flowchart TD
    R(["Row from the file"]) --> S{"servername already in database?"}
    S -- No --> INS["INSERT new server"]
    S -- Yes --> T{"Any value different?"}
    T -- Yes --> UPD["UPDATE this row"]
    T -- No --> N["Do nothing"]

Servers in the database but missing from the file are never read by this query, so they are kept as they are.

What the upsert does, row by row

Server situationActionExplanation
In the file, not yet in the databaseINSERTNew server, it is added.
In the file and in the database, with at least one different valueUPDATEOnly this row is rewritten.
In the file and in the database, strictly identicalNothingNo write. This is the case for the vast majority of rows.
In the database but missing from the fileNothingThe server is kept as it is. An incomplete file deletes nothing.

Why not rewrite everything every time

An UPDATE creates a new version of the row

Postgres does not modify a row in place: it writes a new version and keeps the old one for readers still using it. This is what lets users browse the page during an import without waiting.

Autovacuum later reclaims the space of old versions. It only becomes a problem when rows that did not change are rewritten.

The step 7 query

INSERT INTO patching_server AS t (servername, sub_region, template, ...)
SELECT DISTINCT ON (servername) servername, sub_region, template, ...
FROM patching_staging
ON CONFLICT (servername) DO UPDATE
SET sub_region = EXCLUDED.sub_region, template = EXCLUDED.template, ...
WHERE (t.sub_region, t.template, ...) IS DISTINCT FROM
      (EXCLUDED.sub_region, EXCLUDED.template, ...);  -- only rows that actually changed
